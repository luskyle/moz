# 图纸 → 参数化模型（2D → 3D）

一句话：**现在 moz 只会「吃模型、吐图纸」；这份文档规划另一半——「吃图纸、吐模型」**，两头接上才是
「图纸 ⇄ 模型」闭环。

```
现在：   3D 模型  ──(moz.section/outline + py/moz_drawing.py)──►  2D 图纸（SVG/DXF/PDF）
本方案： 2D 图纸 ──(解析 → 图层语义 → 轮廓修复 → 标注取值 → 成型)──►  3D 模型（可改参数）
```

**为什么要做这件事**（而不是"只解析别人的图纸并显示"）：只显示等于看图软件（eDrawings 之类免费就够）。
变成**模型**才有后面这些：改一个尺寸全模型联动、算重量/材料/报价、干涉检查、出 STEP 给加工、
批量跑、嵌进产线系统。闭环的右半边（3D→图纸）本项目已经做完，缺的是左半边。

## 一、目标与非目标

**目标（P1 就要拿到手）**：给一张 DXF（单视图零件：外轮廓 + 孔 + 标注），产出**可改参数**的实体：

- 改挤出高度、改孔位/孔径 → 重新生成（参数来自图纸标注，不是手敲）；
- 能测体积/面积/重量，能导出 STL 与（已有的）2D 图纸；
- 全过程不引入新的几何内核依赖（走现有 OpenSCAD CSG 通道）。

**先做单视图**：轮廓和尺寸**图纸上已经写死**，不需要猜——这是"图纸→模型"里唯一可靠的部分，
钣金/垫片/激光切割件立刻能用。多视图推深度（主视+俯视对起来）属于"靠人判断"，放 P4 半自动 + 人确认。

**非目标（明确不做）**：

- ❌ 交互式草图 GUI（鼠标画约束草图是 SolidWorks/FreeCAD 的主场，我们做代码/服务/批量化）；
- ❌ "任意图纸一键全自动成 3D"（学术上都没解决，只做半自动 + 可校对）；
- ❌ 在这一层动 C ABI（沿用"优先在 Python 层解需求"的既定策略，C ABI 仍是 25 个函数）；
- ❌ 自己做 B-rep 内核或约束求解器（用成熟开源件，见 §五）。

## 三、P1 的链路规格（逐段可验收）

1. **解析**：用 `ezdxf`（MIT，纯 Python，pip 可装）读 DXF R12–R2018：
   实体清单与统计、`INSERT` 块展开（含嵌套与阵列）、单位与范围（`$INSUNITS/$EXTMIN/$EXTMAX`）、
   图框/视口过滤（`--frame` 排除）。
2. **图层语义**（约定 + 可覆盖）：轮廓层 / 中心线层 / 虚线层 / 标注层。
   默认按层名正则匹配（`OUTLINE|轮廓`、`CENTER|中心`、`HIDDEN|虚线`、`DIM|标注`），命令行可指定
   `--layer OUTLINE`、`--exclude-layer`。
3. **轮廓修复**（这一步决定"能不能用"）：
   重复/重合线段去重、相邻共线合并、圆弧按弦高离散（可配精度）、**缺口检测与桥接**（缺口 ≤ 容差时接上）、
   闭合性判定、内外环归类（包含关系 → 外轮廓 + 孔）、自交/交叉诊断并报告。
   输出一份**修复报告**（"修复了 N 处：去重 6、桥接 2、合并共线 4"），不做静默修补。
4. **标注 → 参数**：读 DXF 的 `DIMENSION` 实体 → 参数表（`名称 → 数值 → 指向的几何`），
   命名标注直接用现成的 `dxf_dim(file, name)` 通道；产出一份 `parameters.json` 便于复用与 diff。
5. **成型**（P1 用现有 CSG 通道）：外轮廓 → SCAD `polygon(points, paths)` → `linear_extrude(高 = 参数)`；
   孔 = 内环 → `difference`；R 圆角 = `offset(r=)`；倒角 = `offset(delta=)`（P1 近似，P2 换真内核）。
6. **反向出图**：复用已有的 `moz.section/outline` + `py/moz_drawing.py`。
7. **入口**：`py/moz_dxf.py`（解析/修复/成型 API）+ `py/dxf_demo.py`（命令行：打印解析与修复报告、
   体积/重量/孔数，按需导出 stl / 图纸）。

## 五、路线与依赖（为什么这么选）

三条可选路线（P1 都不需要，P2 起才分叉）：

| | A：只用 OpenSCAD（CSG） | **B：双内核（推荐）** | C：借 FreeCAD 当后端 |
| --- | --- | --- | --- |
| 做法 | 全部用 SCAD 语义拼特征 | OpenSCAD 管外观/自由造型，OCCT 管结构特征；Python 门面统一 | headless 调 FreeCAD 的 Sketcher/PartDesign/TechDraw |
| 倒角/圆角/抽壳/孔阵列 | 只能近似 | ✅ 内核原生 | ✅ 原生 |
| STEP/IGES | ❌ | ✅ | ✅ |
| 约束草图 | ❌ | ✅（加 planegcs） | ✅ 现成 |
| 新增依赖 | 无 | OCCT 栈（大） | FreeCAD 全栈（最大） |
| 与现有栈 | 无冲突 | 需定"双内核分工规矩" | 与我们的制图层重复 |

**推荐 B**：OpenSCAD 侧继续吃满现有便宜（语义、48 示例、CSG 快速预览、自由造型），
结构件/精确交换交给 OCCT。分工规矩写死：

- **外观/自由造型/快速预览/既有语义** → CSG（OpenSCAD）；
- **结构/孔/倒角/抽壳/精确布尔/STEP 交换** → B-rep（OCCT，经 `build123d`，Apache-2.0 包装）；
- 互操作单向：B-rep ──网格化──► CSG 侧预览；交换格式统一用 STEP。

许可盘点（都可商用，无 GPLv3 纠缠）：

| 组件 | 许可证 | 用途 |
| --- | --- | --- |
| `ezdxf` | MIT | DXF 解析（P1） |
| OpenCASCADE (OCCT) | LGPL-2.1-only + OCCT-Exception 1.0（可闭源链接，需在文档声明） | B-rep 内核（P2） |
| `build123d` / CadQuery | Apache-2.0 | OCCT 的 Python 门面（P2） |
| `planegcs` | LGPL-2.1-or-later | 2D 约束求解（P3） |
| `py-slvs` / `libslvs`（SolveSpace） | GPL-3.0 | **不用**：与我们的 GPLv2 内核混链有冲突风险 |
| LibreDWG | GPL-3.0 | 只允许**独立进程**调用（P4 备选） |
| ODA File Converter | 闭源免费 | DWG→DXF，**不随我们分发**，用户自装（P4 备选） |

## 六、格式与标准（进什么、出什么）

「标准」要分三层看，三层互相不能替代。

### ① 图纸文件格式（事实标准）

| 格式 | 标准化程度 | 能带什么语义 | 我们的定位 |
| --- | --- | --- | --- |
| **DXF** | Autodesk 事实标准（1982 起，规范公开）；2D 交换至今**没有被取代** | 线/弧/多段线/块 + **图形化标注**（`DIMENSION` 实体），无语义 GD&T | **P1 主力**（规范公开、ezdxf 现成、R12 兼容面最广） |
| DWG | 二进制专有，但**交付上的事实标准**；读取靠 ODA / LibreDWG | 比 DXF 富（动态块等），DXF 表达不全 | P4 转换通道 |
| **PDF**（ISO 32000-2、PDF/A-2） | 国际标准 | 冻结的图：矢量线可提取，语义/比例/图层要推；扫描件更难 | P4/P5 —— **工厂之间真正"发图纸"就是发 PDF** |
| **STEP AP242**（ISO 10303-242，Ed 4 = 2025，各大 CAD 已部署） | 国际标准，**唯一带语义 PMI**（GD&T/基准/粗糙度/焊接，绑到面与边） | 3D 几何 + 语义标注（也覆盖 annotated 3D + drawings） | **出口方向**（P2 之后，语义 PMI 算加分项） |
| JT / 3D PDF | 轻量可视化 | PMI 支持有限 | 预览 |
| IGES | 老标准，已被 AP242 取代 | **不能带 PMI** | 不管 |

### ② 图纸"语义"——**没有标准**（这是关键）

DXF 标准化的只是「线/弧/块/标注实体**怎么存**」，没标准化「哪条是外轮廓、这张是主视还是俯视、
⌀16 指的是哪个圆」。所以：

- 本文档里的**「规范化 2D 实体模型」是解析后的内存中间层**（同一层接 DXF/DWG/PDF），
  **不是自造文件格式**——对外仍读写标准格式。类似 ezdxf 有自己的 document 模型、FreeCAD 有自己的
  Draft 对象，没人认为它们发明了格式；
- 需要自定的只是**可配置的约定**（图层名 → 语义的映射、视图划分规则），因为各厂图层命名五花八门；
- 好消息：**标注这一层在 DXF 里是标准化的**（`DIMENSION` 实体），这正是 `dxf_dim(file, name)`
  能按名取值的依据——「图纸驱动参数」有标准可依，P1 就能吃到。

### ③ 制图规范（管"怎么画"，不管文件）

将来（P4 做 GD&T / 剖切符号 / 粗糙度时）要对齐的清单：
ISO 128（技术制图）、ISO 1101（形位公差）、ISO 1302（表面粗糙度）、ISO 2553（焊接符号）、
ASME Y14.41（数字化产品定义）、GB/T 4457–4460（图样画法）、GB/T 14691（技术制图 字体）。

### 结论

- **进**：DXF（P1）→ DWG（P4 转换）→ PDF 矢量（P4/P5）；
- **出**：STEP AP242（P2 之后，语义 PMI 尽力而为）+ 已有的 SVG/DXF/PDF 图纸；
- **不自造格式**；
- 注意：AP242 **能不能带上 PMI 取决于导出方的设置**（实测有大量丢了 PMI 的案例），
  所以语义 GD&T 只作为"尽力而为"的出口能力，**不作为 P1/P2 的验收项**。

## 八、需要拍板的决策点

1. 接受**双内核**（CSG 外观 + OCCT 结构）吗？不接受就只能停在 A 路线（无真倒角/无 STEP）。
2. OCCT 依赖怎么发：服务端 only / 进 wheel（+100MB 级）/ **可选 extra（推荐）**。
3. DWG 走哪条：ODA 转换器（免费闭源、用户自装）还是 LibreDWG（GPLv3、独立进程）。
4. Web 端编辑边界：只做"参数表单/滑块"（推荐）还是要 2D 草图编辑器（成本高一个量级）。
5. P4 自动化边界：半自动 + 人工确认（推荐）还是投研究做全自动。

## 九、风险

- **图纸脏**：真实厂图的缺口/重叠/自交/单位混乱比样例严重得多 → 靠"修复报告 + 人确认"兜底，不做静默修补。
- **双内核语义分叉**：法向、单位、容差、布尔行为不同 → 用 §五 的分工规矩限制交叉，交换一律走 STEP。
- **依赖体积**：OCCT 栈不小 → 可选 extra + 服务端优先。
- **参数化承诺**：P1 的"参数"只是标注读出来的数值（改高度/孔径会重生成）；真正的"给约束自适应"是 P3。
- **图纸→3D 的期望管理**：单视图可做到"可靠"，多视图只能"半自动"，别对外说成自动重建。
