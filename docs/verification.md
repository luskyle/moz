## 为什么不能只用「导出字节相同」当判据

实测（同一几何、同一面数）：下面三种写法**导出字节互不相同**：

```scad
union() { a; b; }     // 显式 union 节点
{ a; b; }             // 裸块（group 节点）
module m() { a; b; }  m();   // 模块体（再多一层）
```

导出面序取决于 CSG 节点结构（以及 `CGALUtils::applyUnion3D` 里按面数排序的优先队列），
而 Python 侧用 API 拼出来的源码不可能在结构上与 `.scad` 逐一复刻。面序不影响几何本身，
所以判据分三档，**后两档也算通过**：

| 档 | 条件 | 说明 |
| --- | --- | --- |
| ① 网格逐字节一致 | 导出字节完全相同 | 最佳 |
| ② 网格作为集合一致 | 三角面多重集合完全相同（每面内顶点排序 + 面之间排序，float32 逐比特） | 只是面序不同 |
| ③ 实体一致 | 体积、表面积、包围盒都在容差内 | CGAL 把同一实体切成了不同三角面 |

容差：体积/表面积**相对 1e-3**、包围盒**相对模型尺度 1e-3**。网格是 float32，
坐标量级几十到几百时每个坐标有 ~1e-5 量化误差，上万面累加后体积/表面积相对误差可达 ~1e-4，
所以 1e-3 留了余量。

2D 几何（svg）用**多边形多重集合**比较多边形顶点（2D 三角化稳定，直接要求集合一致；
若 svg 里出现曲线命令则回落为字节比较并标注）。

`DIFF` 只在**实体真的不一样**时出现，并打印差异数字——典型原因：少了 `$fn`、少了某个对象、
平移/旋转顺序错、参数语义搞错（`offset` 的 `r` vs `delta`）。

## 差异怎么定位

脚本给出的信息够用来缩小范围：

1. **空几何不一致** → 十有八九是外部文件路径写错（相对路径会静默变空）或 `use` 找不到库。
2. **维度不一致** → 2D/3D 搞错了（例如漏了 `linear_extrude`）。
3. **几何不一致 + 面数差很多** → 少/多对象、`$fn` 没复现、布尔层级错。
4. **几何不一致 + 面数接近** → 参数语义或数值精度（`offset` 的 `r/delta`、
   `cylinder` 的 `r1`、三角函数末位、浮点累加顺序）。

需要更细时，把原文件拆成几个子表达式分别 `moz.eval_text` 与 Python 侧对照
（看 `dimension`/`is_empty`/面数/体积），这类分件比对在本次改造里定位了不少问题
（例如 `offset` 首参语义、`slices` 默认值、`$fn` 泄漏）。

## 局限

- 判据是**几何层面**的，不检查颜色（颜色由 `moz_geom_face_colors` 单独验证）、
  不检查 `#`/`%` 的预览效果。
- 某些示例原生求值很慢（`Old/example006`/`example024` 各约 30 s、`Basics/CSG-modules` 约 15 s），
  全量跑一次约 7 分钟。
- 脚本需要能构建/加载 `libmozopenscad.so`；`Old/example023` 还需要 `3rd/openscad/libraries/MCAD/fonts.scad`
  （仓库自带的 drop-in 字形表；缺了会报 `SKIP` 并说明）。
